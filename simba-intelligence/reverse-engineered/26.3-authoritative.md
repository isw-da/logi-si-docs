# Simba Agentic Intelligence 26.3: authoritative pre-release notes

**Status: 26.3 is UNRELEASED at the time of writing (29 September 2026).** The Composer
release that carries it, SCP `26.3`, is dated 30 September 2026 and is not marked released.
Nothing below was observed on a running 26.3 instance, because none exists yet. Every
statement is subject to change up to and after that date. `26.2-authoritative.md` remains
correct for 26.2 and is not superseded by this file.

This file exists because the mirrored upstream pages under
`simba-intelligence/pages/simba-intelligence/docs/` still describe 26.2 and, in fifteen
places across eleven pages, describe a thing 26.3 changes. The mirror must stay a faithful copy of upstream, so
none of those pages has been edited. The corrections live here. Section "Mirrored pages this
file supersedes" lists them by path.

Scope: this is an operational file. It records the things that make a reader following the
mirrored documentation run a command or write code that breaks. It is not an announcement,
it carries no commercial or entitlement detail, and it deliberately omits anything that is
neither operationally necessary nor citable.

Sources are Jira keys in `PY` (Simba Agentic Intelligence, "SI" below), `SCP` and `CMP`
(Composer), Confluence page ids in the SCP and PJX spaces, and the public Composer
documentation site. Public facts carry their public URL.

---

## 1. Deployment: SI is no longer its own Helm deployment

The single largest breaking change, and the one that invalidates the most mirrored text.

- SI ships as a sub-component of the Composer / Self-Service Analytics Helm chart from 26.3
  (PY-693). The standalone SI chart is deprecated (PY-701).
- The arrangement of a separate SI chart pointing at an externally hosted Composer is
  recorded as "Configuration no longer supported in 26.3+" (Confluence page 18711380170, SCP
  space, 10 September 2026).
- A standalone SI customer with no BI **must still deploy the Composer / SSA chart**. That
  is a requirement of the packaging, not a convenience.
- The transition guide for existing deployments is ticket **PY-706**, which was unfinished
  when this was written. There is no documented upgrade path to point at yet. Do not
  improvise one: nobody in this run has installed 26.3.

Composer's own 26.3 documentation is public and states verbatim that "Kubernetes is
supported for new installations only for version 26.3 and later", with Helm chart
`composer/composer`:
<https://insightsoftware.mintlify.app/simba-embedded-analytics/docs/self-service-analytics/26.3/>

This bears directly on SI, which deploys on Kubernetes. It is the only part of the 26.3
deployment story with a public source.

**Context path.** SI moves from root `/` to `{composer-context}/intelligence` (page
18711380170). Bookmarks and API clients built against the root path break. The context path
stays configurable, so a `/discovery` literal survives where an admin sets it and stops
being the default.

**The SI UI and its related frontend APIs are removed** (page 18711380170). A breaking
change, not a redirect.

**Symphony MDR customers** must move to Dundas first, and Dundas integration with SI is
recorded as not available, so that path yields no AI experience at all (page 18711380170).

## 2. Sign-in: SI abolishes its own login

Single sign-on with Composer is **not new in 26.3**. It shipped in 26.2 under PY-530
(Confluence PJX/18483511372, 29 June 2026), and `26.2-authoritative.md:29` already records
it.

What 26.3 adds is that SI stops having a login of its own, so it **inherits** Composer's
SAML rather than implementing SAML. PY-689 states the reason plainly: SI's own login does
not work with SAML, Composer's does. There is no implementing SAML ticket in PY. SAML was
exercised against a 26.3.0 build under SCP-454 and CMP-8739.

This matters for how the change is described. The mirrored
`guides/admin-guides/Administrator-Guide.md:340` **already claims** SAML, OIDC and LDAP
identity-provider configuration. So "SAML is now available" is the wrong claim. The accurate
one is: SAML reaches SI through Composer's sign-in experience, because SI no longer has a
sign-in of its own.

One Composer defect remains open: **SCP-1124** records the Custom User Attribute fields on
Composer's SAML admin page as not editable, leaving attribute mapping unusable from the UI.
`saml.useMultiValueList=false` is configuration, not a defect.

## 3. Native MCP gains visual tools, with a deployment precondition

26.3 adds MCP tools for creating, retrieving and rendering visuals, and for opening a
generated visual in Composer. The originating design is Confluence PJX/18246598721
(24 April 2026).

`mcp-claude-integration.md` and `26.2-undocumented-features.md` both record the live 26.2
tool surface as exactly four read-only tools (`get_data`, `search_data_sources`,
`get_suggested_questions`, `get_field_statistics`), with `prompts` and `resources` empty.
That list is a 26.2 capture and does not survive 26.3. **The 26.3 tool names and parameters
are not recorded anywhere in the sources available here, so they are not stated. Re-probe a
running 26.3 instance.**

Three qualifications that must travel with the claim.

- **This is not "you can now create visuals by asking".** Composer 26.2 already shipped
  visual creation from natural-language prompts from the home page, the Visual Gallery and
  inside dashboards. What changes in 26.3 is the rendering surface moving into the AI client.
- **Dashboards are out of scope and unscheduled.** PY-631 sits in the backlog with no
  fixVersion, and PY-536 deferred `get_dashboards` explicitly. A Q4 2026 planning draft
  (PJX/18846908494) puts dashboards and reports out of scope for that quarter too. Do not
  read dashboards as next.
- **Deployment precondition.** MCP must be served at root (`/`) or disabled entirely (page
  18711380170), described there as a protocol limitation and explicitly not fixed for 26.3.
  That sits awkwardly beside the context-path move in section 1, so read the page before
  planning a deployment around both.

26.3 also hardens the MCP OAuth flow (server-side request validation, PKCE enforcement,
exact redirect matching, safer token handling) and adds a breaking change requiring the
canonical MCP base URL plus a trusted-access flow.

On feasibility, for anyone integrating against a non-Claude client: the MCP specification
already allows a tool result to carry an image block, so a server can render a chart and
return a PNG without any extension. The mechanism that matches "displayed within the AI
experience" is MCP Apps (SEP-1865), where a widget registers as a
`ui://widget/<name>.html` resource with MIME type `text/html+skybridge` and the resource's
`_meta.ui.domain` is derived from a SHA-256 of the server URL. That path is verified for
Claude only. The Copilot and ChatGPT cases were not settled. SEP-1865 is a proposal against
the Model Context Protocol specification, not an insightsoftware artefact, and is named here
only so the mechanism can be looked up.

## 4. Administration moves under Composer

LLM Configuration and Agentic Rules move under Composer's **Administration > Tools** area
(Confluence page 18773016632, 11 September 2026). The unification is scoped to exactly four
items, LLM Configuration, Agentic Rules, Chatbot and Help Links, under epic **SCP-314**
(page 18657935398, 20 August 2026).

This invalidates the navigation instructions in the mirrored
`guides/user-guides/Rules-Management-Guide.md` at lines 131 and 163, both of which route the
reader to a **Rules** entry in the SI user menu at the top right.

Existing rules keep working: SCP-313's test pass includes the case that the rule engine is
unchanged. SCP-312 covers credential masking, audit logging with user identity and
timestamp, and licence switching with no reinstall.

Two licence behaviours that are operational rather than commercial:

- A Composer-only licence **hides both menus and blocks their direct URLs** (SCP-312), and
  removes the AI surface from the Composer UI (SCP-487).
- Rules and LLM configuration **survive a downgrade** rather than being deleted (SCP-312).

**On caching, do not read this as a new capability.** A rule-aware cache was already claimed
for 26.2 under PY-498, which `26.2-authoritative.md:50` records. What 26.3 adds is
rule-fingerprint validation and improved semantic-cache invalidation when data sources or
rules change. Whether that completes PY-498 or re-announces it cannot be determined from the
available sources.

## 5. Data sources: joins and output configuration editable by chat

**PY-709 makes existing joins editable through chat.** The agent can change a join's type
(inner, left, full outer) or the columns it matches on, and refuses cleanly when asked to add
a table, remove a join or flip a join's direction. A column change must match a known
relationship. The PR landed 15 September, the QA brief 17 September, and all nine scenarios
were signed off on 24 September, verified in both the chat summary and Composer's data source
editor.

This supersedes the mirrored `guides/user-guides/Data-Agent-User-Guide.md:370-377`, which
sends the reader to the Data Sources interface to modify field selections and add calculated
fields or custom metrics, and `getting-started/Quick-Start-Guide.md:103`, which describes
source creation as a single-shot review-and-approve.

**Do not pair this with rollback.** The snapshot taken after an agent edit **cannot be
restored in 26.3**: the Composer UI to restore snapshots does not exist yet, so the snapshot
is write-only.

**Still open: CMP-10625** reports that output configuration (derived fields, hierarchy
fields, custom metrics, field formatting) is wiped when joins are added or changed. It was
closed as a duplicate into a parking lot and the surviving duplicate was never identified.
It is unresolved rather than fixed, and it bears directly on the conversational
derived-fields claim.

Also in this area: creation tasks now report non-fatal failures instead of appearing to
succeed with no source created, the legacy streaming Data Source Agent endpoints are
deprecated, and the old execution paths are removed (PY-691, PY-695, PY-700, PY-705, PY-709;
Confluence page 18731368546).

## 6. Claude models on Azure AI Foundry

**The provider is Azure AI Foundry, not Azure OpenAI**, and this distinction is the whole
point of the section.

The mirrored `guides/admin-guides/LLM-Provider-Configuration.md:35` carries a single Azure
OpenAI row, and `reference/supplementary-resources/Glossary.md:15` lists supported providers
as Google Vertex AI, Azure OpenAI and AWS Bedrock. Neither mentions Foundry.

- Claude **already ships in SI via AWS Bedrock** and has since before 26.3. The novelty is
  Claude on Azure, not Claude in SI. Writing "SI now supports Claude" is wrong.
- The configuration is the **Anthropic shape, not the Azure OpenAI shape**. Foundry hosts the
  raw Anthropic API and SI uses `langchain-anthropic` with `base_url` pointed at the Azure
  endpoint. The `deployment_name` requirement that applies to Azure OpenAI **does not carry
  over**.
- **There is no embeddings model on Claude via Foundry.** A second provider is required for
  embeddings. A Foundry-chat-plus-Azure-OpenAI-embeddings pairing was tested and worked, but
  across two hosts. The single-endpoint case was not confirmed.

PY-547 carries the work. Chat, streaming and tool calling were exercised against a real
Foundry deployment on 12 June 2026, two months before the ticket resolved on 20 August. There
is **no post-implementation QA record**, and the docs ticket PY-698 is still In Review with no
fixVersion, so shipped parameter names are inferred from PY-547 rather than observed.

Independently, Microsoft documents Claude models as GA on Azure AI Foundry, with endpoint
`https://<resource>.services.ai.azure.com/anthropic/v1/messages` and an `anthropic-version`
header, which corroborates the Anthropic shape:
<https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/models-sold-directly-by-azure>

**Air-gapped consequence.** The mirrored
`deployment/installation-and-setup/Air-Gapped-Deployment.md:231` maps Azure OpenAI to
`*.openai.azure.com` only. A Foundry endpoint resolves elsewhere, so that allowlist is
incomplete for a Claude-on-Azure deployment. The exact hostname to add is not recorded in any
source available here.

## 7. Workspaces

New in 26.3 (epic SCP-165, still in Validating at the time of writing). Described in
Confluence page 18715705405 (SCP space, 16 September 2026) and exercised in page 18773868551,
the 26.3 workspace regression checklist (24 September 2026, passing on Chrome and Edge). A
workspace holds data sources, with versioning (restorable, configurable retention), Open and Published
states, all-or-nothing publish with automatic rollback, and Create New versus Update
Original.

The mirrored `guides/user-guides/Data-Source-Optimization-Guide.md:263-268` documents the
manual "draft in a sandbox data source, promote to shared environment" pattern. Workspaces
are the supported replacement for that pattern, subject to the limits below.

Limits that a reader will otherwise hit:

- **A published workspace is permanently read-only** (SCP-909). To keep iterating, create a
  new workspace.
- **Concurrent edits are not reconciled.** Last publish wins, with no diffing (page
  18715705405).
- **Deleting a workspace hard-deletes unpublished artefacts** (page 18715705405).
- **There is no whole-workspace export or import**, and it is recorded as "Not planned"
  rather than deferred (page 18715705405).
- The UI does not distinguish published from unpublished artefacts (planned, SCP-693).
- **Prerequisites: Enhanced Mode plus a configured LLM.** The regression checklist (page
  18773868551) tests both before anything else.
- Workspaces are gated on the `SIMBA_INTELLIGENCE` licence flag.
- **Workspaces are single-user and cannot be shared, and no ticket exists to lift that.**
  SCP-303 built a `workspace_member` table with OWNER, EDITOR and VIEWER roles and invite
  columns, and nothing consumes it. SCP-105's spike was titled "Intelligence Workspace /
  Multi-Player", so sharing was scoped and dropped. There is no ticket for visuals or
  dashboards in workspaces either.

Unresolved, and worth knowing before promising consistency: a planning draft
(PJX/18820366454, 21 September 2026) records that the same question asked by different users
is treated by the query agent as a unique question each time, which can produce different
answers to the same question. The proposed fix is a Q4 2026 draft. No 26.3 mitigation was
found; the cache and rule-fingerprint work is a different thing.

## 8. Four claims that read as new and are not

Collected here because each one, written unqualified, is a false statement about 26.3.

1. **"SI now supports Claude."** Wrong. Claude already ships via AWS Bedrock, recorded in the
   mirrored LLM configuration guidance. 26.3's novelty is Claude on **Azure AI Foundry**.
2. **"26.3 adds a rule-aware cache."** Wrong, or at least unprovable. PY-498 already claimed
   a rule-aware cache for 26.2. State what 26.3 adds, which is rule-fingerprint validation
   and improved semantic-cache invalidation.
3. **"SAML is now available."** Wrong. `Administrator-Guide.md:340` already claims SAML. The
   change is SAML **through Composer's sign-in**, because SI abolishes its own login.
4. **"You can now create visuals by asking."** Wrong. Composer 26.2 already shipped visual
   creation from natural-language prompts from several entry points. The change is the
   **rendering surface** moving into the AI client.
